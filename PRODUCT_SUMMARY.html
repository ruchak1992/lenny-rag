Lenny-RAG — Product Summary

As of 2026-10-31

Problem

Lenny's Podcast has about 300 episodes of top-tier product thinking, but you can't search across it. The advice is there, just impossible to pull up during a strategy review or a product diagnosis.

Solution

You ask a product question in plain English. The tool finds the most relevant transcript passages, and Claude answers from those passages alone. Each point cites its episode, and the advice is applied to Glance when the question is about Glance.

How it works

  1. Ingest: Split all 299 transcripts into 13,204 overlapping chunks of about 500 tokens. Each chunk is embedded with Voyage and stored in a local ChromaDB database.
  2. Retrieve: Embed the question the same way, pull the 30 closest chunks, then have a reranker pick the best 8.
  3. Generate: Claude Sonnet answers using only those chunks, with [Episode] citations.
  4. Use: A command-line tool for quick tests, and a simple Streamlit web app with an expandable list of sources.

Models and RAG techniques

Answers come from Claude Sonnet 4.6 (claude-sonnet-4-6, up to 1,500 tokens), embeddings from Voyage voyage-3.5, and reranking from Voyage rerank-2.5.

Techniques used

  1. Chunking with overlap: About 500-token chunks, each sharing 50 tokens with the next, so an idea isn't cut in half. A short leftover at the end of a transcript is folded into the chunk before it, so no chunk is under 100 tokens.
  2. Semantic search: Questions and chunks are compared by meaning (cosine similarity of embeddings), not keywords.
  3. Separate settings for questions and documents: Voyage embeds short questions and long passages differently.
  4. One embedding model for both sides: Ingestion and queries must match, so the model is a single shared setting.
  5. Two-stage retrieval: A fast vector search finds 30 candidates, then a reranker reads the question and each candidate together and keeps the best 8. That's enough context for a nuanced answer without filling the prompt with noise.
  6. Grounded answers: Claude may use only the retrieved excerpts.
  7. Citations on every claim: Each chunk carries its episode name.
  8. Saying "not covered": Claude must say so rather than guess.
  9. Safe re-runs: Fixed chunk IDs mean already-stored chunks are skipped.
  10. Retrieval evaluation: A set of 40 questions with known answer episodes scores every change before it ships.

Not used yet: Hybrid keyword search (BM25), contextual chunk headers, speaker-turn chunking, query rewriting, and conversation memory.

Product decisions

  • Accuracy over fluency: If the transcripts don't cover a question, it says so instead of guessing.
  • Trust through citations: Every claim names its episode, so you can check it.
  • Cost guardrails: It runs a 5-transcript test first and skips chunks that are already stored. The whole corpus costs under $1 to embed, and each query costs a few cents.
  • A deliberately small v1: No chat memory, auto-ingesting new episodes, or multiple users.
  • One change at a time: Each retrieval change is measured on its own, so we know which one helped.

Retrieval improvements (2026-10-31)

Three changes, each made to fix a specific problem and each measured before and after. Full detail is in CHANGELOG.md.

1. Reranking

Why: Vector search ranks chunks by how close their topic is to the question, not by whether they answer it. For "What does Shreyas Doshi say about the LNO framework?", 4 of the 8 chunks were unrelated career advice from other guests.

What changed: Retrieval now pulls 30 candidates, and Voyage rerank-2.5 scores each one against the question and keeps the best 8.

Observed: On the LNO question, all 8 chunks now come from Shreyas Doshi episodes, including one that had been ranked #25. Across the 40-question test set:

Vector search only28/4034/4040/400.80
+ reranking33/4039/4040/400.90

MRR (mean reciprocal rank) is 1.0 when the right episode is always first and falls as it ranks lower. The extra cost is a fraction of a cent and a few hundred milliseconds per question.

2. Removing junk tail chunks

Why: The chunker left a short scrap at the end of many transcripts. 75 of 299 episodes ended in a chunk under 100 tokens, 9 of them under 10 tokens (literally "." or " episode."). 46 of these scraps held no new text at all. Near-empty chunks look vaguely similar to everything, so for "What is the best pizza place in Goa?" the #1 result was a chunk containing only a full stop.

What changed: A short leftover is now folded into the previous chunk, and the whole corpus was re-embedded into a fresh index. The old index is kept as a backup.

Observed: Chunks went from 13,279 to 13,204, and none is under 100 tokens. The junk chunk no longer tops off-topic searches. Test-set scores didn't change, which is expected, because junk chunks only win when no real chunk matches.

3. A retrieval test set

Why: Until now, quality was judged by eye on a few questions, so there was no way to tell whether a change helped.

What changed: We added 40 questions, each tagged with the episodes that answer it (13 use the framework's name, 24 describe the idea without naming it, 3 are about Glance), and a script that scores retrieval. Every expected episode was checked against the transcript text. One false match was caught this way: a search for "DORA" matched 23 times in an episode that never discusses it.

Observed: It produced the reranking numbers above. It's also too easy: every question already finds the right episode somewhere in the top 8, so it needs harder questions before it can measure the next changes.

What we learned

  • The reranker's score can't decide "not covered" by itself yet. The off-topic pizza question's best match scored 0.46, and a real Glance retention question's best scored 0.56. That's too close for a reliable cutoff, so Claude's "not covered" rule is still the safety net.
  • Reranking fixes ranking, not missing results. If the right chunk isn't among the 30 candidates, reranking can't bring it back. The Glance retention question needs better recall, not better ordering.
  • Any change to chunking means re-embedding everything. Chunk IDs are reused, so the old index has to be rebuilt from scratch.

Recent maintenance

Voyage retired the voyage-3 embedding model the tool was built on, so every query failed. We moved it to voyage-3.5 and re-embedded the full corpus. That should have cost $0, since about 6.6M tokens fits inside the 200M-token free tier. The model name now lives in one shared setting, so ingestion and queries can't use different models again. The app is running, and the fix is committed on the voyage-3.5-migration branch but not pushed.

Next

  • Not measured yet: The PRD target that 7 out of 10 answers feel useful.
  • Harder test questions: Questions about details deep inside episodes and questions that need several guests, so the test set can show further gains.
  • Next retrieval changes, measured one at a time: Add the episode name and topic to each chunk before embedding (contextual headers), then split chunks on speaker turns instead of token counts.
  • Possible next features: Hybrid keyword search, follow-up questions, and adding new episodes automatically.
  • Worth adding: A simple alert for when a provider retires a model, since this break went unnoticed.
